## 1. 目标

把当前可以打开的 Diet Tracker 第一版，推进为能够由真实用户持续使用、检查和迭代的产品。

本轮需要同时验证四件事：

1. 用户能否完成第一版完整任务。
2. 页面是否覆盖默认、加载、空、错误、禁用、成功和边界状态。
3. 页面显示的数据是否来自真实 Supabase，并且计算、保存和重新读取结果一致。
4. 测试中发现的设计、前端、后端和新需求问题能否进入统一闭环。

## 2. 任务组织决定

继续使用 `梳理饮食追踪项目进度` 作为唯一产品主任务，不再创建第二个产品主任务。

原因如下：

1. `docs/feature-requests.md` 已经明确该任务负责需求记录、优先级、范围和验收。
2. 新建另一个产品主任务会产生两个决策来源，需求状态和验收结论容易冲突。
3. 测试执行会产生大量截图、复现步骤和回归结果，适合单独建立测试任务，但产品决定仍回到原产品主任务。

建议新增一个专项任务：

```text
Diet Tracker 第一版体验测试与验收
```

## 3. 各任务职责

| 任务 | 负责内容 | 不负责内容 |
|---|---|---|
| 产品主任务 | 测试范围、问题定级、优先级、需求状态、验收标准、发布决定 | 不直接替专项任务修改实现 |
| 体验测试任务 | 按真实用户路径操作、保存证据、复现问题、执行回归 | 不自行决定新字段或新功能 |
| Figma 设计任务 | 修改流程、页面、组件及各种状态，维护设计来源 | 不把静态示例解释为后端能力 |
| React 前端任务 | 实现已批准设计、接入已支持契约、处理界面状态、发布 Preview | 不自行增加字段、RPC 或 View |
| Supabase 后端任务 | 账号、数据正确性、RPC、RLS、测试数据和数据契约 | 不替产品决定交互流程 |

## 6. 测试推进阶段

### 阶段 0：建立可测试环境

1. 让正式体验账号可以登录生产环境。
2. 确认正式体验账号与测试账号数据隔离。
3. 确认线上地址使用最新 Production 部署。
4. 为正常、空、错误和边界场景准备可识别的测试数据。
5. 记录每个测试数据由哪个账号、日期和场景使用。

### 阶段 1：完整主流程

按以下顺序完成一次不中断的真实使用：

```text
登录
→ 查看今日汇总
→ 新建一餐
→ 添加成品
→ 添加单品
→ 修改份数
→ 保存
→ 返回今日页
→ 编辑刚保存的餐次
→ 删除一个项目
→ 再次保存
→ 刷新页面
→ 退出登录
```

这一阶段只确认任务能否完成，不在操作途中修改设计。

### 阶段 2：关键状态

分别验证：

1. 默认状态。
2. 加载状态。
3. 空状态。
4. 错误状态与重试。
5. 禁用状态与重复点击保护。
6. 保存成功状态。
7. 保存失败后草稿保留。
8. 登录过期和权限错误。

### 阶段 3：数据正确性

逐层核对：

1. 餐内项目营养之和是否等于餐次营养。
2. 所有餐次营养之和是否等于今日汇总。
3. 新增或编辑餐次后，刷新页面是否仍显示相同结果。
4. 成品和单品的名称、说明、估算标记、剩余份数和最近使用日期是否完整。
5. 已用尽成品是否不再出现在选择器中。
6. 目标为空或营养超过目标时，界面是否仍能正确表达。
7. 页面显示的舍入结果是否一致，任何无法解释的差异都记录为数据问题。

### 阶段 4：界面和设备

验证：

1. 320px 左右的小屏幕。
2. 常见手机宽度。
3. 手机软键盘弹出时的输入和按钮可达性。
4. 长页面滚动。
5. 超长名称。
6. 大量餐内项目。
7. 小数份数。
8. 错误提示、禁用按钮和加载反馈是否清晰。

### 阶段 5：问题分流和实现

| 问题类型 | 处理流程 |
|---|---|
| 纯视觉问题 | 产品确认目标 → Figma 修改 → 前端实现 → Preview 验证 |
| 交互流程问题 | 产品主任务确认流程 → Figma 补齐状态 → 前端实现 |
| 前端实现错误 | 前端修复 → 自动测试 → Preview 回归 |
| 数据显示错误 | 前端确认映射 → 后端确认 RPC 数据 → 联合修复 |
| 测试数据不足 | 后端准备测试数据，不在页面写死示例 |
| 新字段或新能力 | 产品建立 FR → 前后端评估 → approved → backend_ready → frontend_connected |
| 线上部署问题 | 前端检查构建和环境变量 → Vercel Preview → Production |

### 阶段 6：回归和发布

每批修改完成后：

1. 先在 Vercel Preview 验证。
2. 重测被修改功能。
3. 重测它的前后相邻流程。
4. 重测保存失败、登录过期和草稿保留。
5. 重测手机屏幕和软键盘。
6. Preview 通过后再进入 Production。
7. Production 再执行一次核心主流程。

严重程度定义：

| 等级 | 判断标准 |
|---|---|
| P0 | 无法登录、数据越权、数据严重损坏或核心服务不可用 |
| P1 | 核心流程无法完成、保存结果错误或数据明显不一致 |
| P2 | 有替代路径，但交互、状态、响应式或局部数据存在问题 |
| P3 | 视觉细节、文案和不影响任务完成的问题 |

## 8. 第一版验收标准

第一版只有同时满足以下条件才能验收：

1. 正式体验账号可以稳定登录和退出。
2. 登录、今日、新建餐次、添加成品、添加单品、编辑和保存主流程通过。
3. 保存后刷新页面，数据仍然正确。
4. 今日汇总、餐次和餐内项目之间没有无法解释的营养差异。
5. 加载、空、错误、禁用、成功和关键边界状态均已验证。
6. 保存失败时全部草稿保留，并允许用户主动重试。
7. 登录过期和 RLS 权限错误会返回登录页，不显示其他用户数据。
8. 320px 左右的小屏幕、手机软键盘和长页面不会阻断核心操作。
9. P0 和 P1 问题全部关闭。
10. 已修复问题完成 Preview 和 Production 回归。
11. 厨房和采购仍保持明确占位，不暗示未支持能力已经可用。
12. FR-001 等未批准需求没有被提前实现。
