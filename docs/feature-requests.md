# Diet Tracker · 需求与思考记录

最后更新：2026-07-16

## 1. 这份文档的作用

这份文档是三个 Codex 对话共享的需求记录，也是产品思考过程的长期存档。

它负责保存：

1. 新想法最初是怎么产生的。
2. 用户希望解决什么问题。
3. 界面、前端和后端分别受到什么影响。
4. 讨论中考虑过哪些方案。
5. 最终采用或放弃了什么，以及原因。
6. 需求后来发生过哪些变化。

已经确认并可以执行的接口定义写入 `docs/data-contract.md`。本文件不代替数据契约。

## 2. 三个对话的职责

| 对话 | 职责 |
|---|---|
| 梳理饮食追踪项目进度 | 产品主对话。记录想法、梳理使用流程、决定优先级、汇总前后端反馈并验收 |
| 当前后端对话 | 评估数据库、Supabase、安全、数据迁移和接口影响，并完成后端实现 |
| 开发 diet-tracker React 前端 | 评估页面、交互、客户端状态和接口接入，并完成前端实现 |

## 3. 状态定义

| 状态 | 含义 |
|---|---|
| `idea` | 正在记录和梳理，还没有要求前后端实现 |
| `needs_review` | 等待前端或后端评估 |
| `approved` | 产品方案已经确认，可以安排实现 |
| `backend_ready` | 后端已经完成并验证，前端可以接入 |
| `frontend_connected` | 前端已经接入，等待整体验收 |
| `done` | 已经验收完成 |
| `paused` | 暂时不做，但保留思考过程 |
| `rejected` | 决定不做，必须记录原因 |

## 4. 共同工作规则

1. 新需求不能只保存在某个对话中。主对话需要为它建立一个需求编号。
2. 三个对话开始相关工作前，都先读取本文件和 `docs/data-contract.md`。
3. 界面产生新数据需求时，先记录需求，再由前后端分别评估。
4. 前端不能根据界面自行增加数据库字段。后端也不能在产品流程未确认时替产品做决定。
5. 后端完成数据库迁移或接口后，需要同步更新 `docs/data-contract.md`。
6. 每次需求内容、状态、方案或负责人发生变化，都要在该需求的“更新记录”中追加一行。旧记录不得覆盖。
7. 对话之间的消息只负责提醒。完整信息以本文件和 `docs/data-contract.md` 为准。

## 7. 需求详情

### FR-001 · 小票导入库存与食材匹配

**状态：** `frontend_connected`
**提出位置：** 当前后端对话  
**当前负责人：** 产品主对话验收
**最后更新：** 2026-07-15

#### 原始想法

单品选择器是否可以通过识别购物小票，把购买的商品直接接入饮食追踪工具。

2026-07-14 产品决定后，需求名称从“小票识别并导入单品”调整为“小票导入库存与食材匹配”。小票第一版不直接生成可记餐单品，而是先进入库存；只有匹配到已有食材并具备标准份量的数据，才可以继续进入单品选择器。

#### 希望解决的问题

减少手动搜索和录入购买食品的操作。用户买完食物后，不想再次手动把蓝莓、鸡蛋、牛奶这类商品逐个搜索、添加到工具中。

#### 产品流程草案

第一版产品路径按“库存导入”处理，不直接把小票商品变成可记餐单品。

```text
厨房首页
→ 添加冰箱库存
→ 拍照导入小票
→ 上传后进入识别中状态
→ 系统生成待确认小票草稿
→ 用户逐项确认、修改、忽略或合并
→ 确认入库
→ 商品进入冰箱库存
→ 后续在做饭流程或库存列表中使用这批数据
```

PDF 导入暂缓，不进入 FR-001 第一版后端实现。前台可以保留未来入口或显示未开放状态，正式可用能力先以照片导入为准。

用户确认页需要按识别状态分层：

1. 已匹配已有食材：显示标准名称、量词、数量，用户只确认数量和存放位置。
2. 可能匹配：显示原始小票名称和推荐匹配项，用户选择正确食材。
3. 未匹配：用户可以改名、选择已有食材、标为库存占位，或进入后续营养信息补充。
4. 非食物或不追踪项目：用户可以忽略，不写入库存。

“开始使用这批数据”的第一入口是库存，不是记餐。

1. 在厨房首页的“冰箱库存”看到新增商品。
2. 在做饭流程中从库存选择食材，并确认本次用量。
3. 已匹配到 `ingredients` 且已有营养和标准份量的数据，才可以进入单品选择器。
4. 未匹配商品允许进入库存，也允许在做饭流程中被选用；它不直接参与单品营养计算。
5. 未匹配商品后续需要通过营养标签拍照补充 Nutrition Facts Label。补充完成并生成可用营养与标准份量后，才可以进入单品选择器。营养标签拍照、自动建食材和单品选择器扩展属于第二版，不进入 FR-001 第一版后端实现。

#### 当前尚未确认的问题

1. OCR/AI 识别由后端/Supabase Edge Function 或等价服务端能力处理，前端不暴露第三方密钥，也不在界面强调 AI 参与。
2. 需要保存小票图片原图、识别文本和导入历史的具体保留范围，由后端在实现评估中确认。
3. 当前 `inventory` 不足以承载小票草稿，需要新增小票导入草稿表、草稿条目表和商品别名表。
4. 商品匹配已有 `ingredients` 的规则以别名匹配和人工确认为主。AI 或 OCR 只提供建议，不直接替用户确认。
5. 未匹配商品允许创建库存占位项，也允许在没有营养数据时进入做饭流程。
6. FR-001 第一版只支持照片导入。PDF 暂缓。
7. 入库确认后是否支持撤销或回滚本次导入，仍由后端评估事务和库存流水可行性后确认。

#### 候选方案

**方案 A：库存优先，推荐。**
小票识别结果只进入库存确认流程。只有匹配到已有 `ingredients` 的商品才和营养系统产生连接。优点是符合当前厨房设想，风险低，不会把无营养数据商品误当作可记餐单品。缺点是不能立刻解决“单品选择器自动新增大量商品”。

**方案 B：食材库优先。**
小票商品确认后直接创建或补充 `ingredients`。优点是单品选择器增长快。缺点是小票通常没有营养信息，容易制造不可计算或错误计算的数据。

**方案 C：混合导入。**
确认页让用户选择“入库存”或“加入食材库”。优点是灵活。缺点是第一版交互和数据模型更复杂，容易把库存、食材库和营养库混在一起。

当前产品决定采用方案 A，并明确分两版推进：第一版只做照片小票导入库存和已有食材匹配；第二版再做营养标签拍照、自动建食材和单品选择器扩展。

#### 前端评估

前端已接入厨房首页、冰箱库存、照片导入、识别中和小票确认流程。照片只接受 JPEG、PNG、WebP，最大 10MB。PDF 入口保持禁用并标明未开放。

确认页按已匹配、需要确认、未匹配和已忽略分组。当前契约只返回一个可能匹配建议，没有全量食材搜索接口，因此第一版支持接受该建议、改为库存占位或忽略，不自行扩展食材搜索能力。名称、数量、量词和存放位置使用本地草稿；已修改草稿离开前提示，保存失败后保持全部修改。

上传、识别和确认均通过独立适配层调用真实 Supabase。`OCR_NOT_CONFIGURED` 会显示“照片已保存但识别服务尚未配置”，不会生成示例商品行。确认使用幂等键，提交中禁用按钮，网络结果未知时保留原键并允许查询结果或原键重试。确认成功后重新读取库存和厨房首页。

未匹配库存已经接入做饭库存选择器。保存成品时使用 `p_unmatched_items` 单独提交，因此可以真实扣减库存，但不会伪造食材身份或计入营养。

2026-07-15 按 Figma `厨房 · 小票确认 · DS统一迭代 v2 · 简化确认卡片` 完成前端调整。确认卡片现在使用数量步进、紧凑量词输入和 `常温`、`冷藏`、`冷冻` 三段选择。缺失数量或量词时禁用确认按钮并显示汇总提示，不再为每张卡片常驻显示校验错误。疑似把价格识别成数量时，前端只采用“`rawQuantity` 与 `rawPrice` 相同且没有 `rawUnit`”这一窄规则清空数量并要求人工确认。这是临时安全规则，不替代后端的数量置信度判断。

当前契约仍有三个缺口。第一，确认入库仍强制要求 `confirmedUnit`，Figma 没有定义 OCR 缺失量词时的可靠来源，因此前端保留紧凑量词输入，不能自动编造。第二，契约没有数量字段置信度或“疑似价格”标记，前端不能覆盖更多 OCR 歧义。第三，契约只提供单条食材匹配建议，没有确认页全量食材搜索接口，因此卡片只能采用真实建议、改为库存占位或忽略。

#### 后端评估

**结论：** 当前 `inventory` 表可以保存确认后的库存行，但无法承担小票草稿和导入历史。采用“库存优先”需要新增导入主表与条目表；建议同时加入别名表，以便人工确认过的商品在下次导入时自动匹配。2026-07-14 产品主对话已确认第一版范围，后端可以按“照片小票导入库存与已有食材匹配”进入实现。

##### 1. 当前数据库的支持边界

`inventory` 已有 `ingredient_id`、数量、单位、存放位置、购买日期、价格和 `receipt_raw_name`。因此，一条确认过的小票商品可以写入一条库存记录：匹配成功时填写 `ingredient_id`，未匹配时保持 `ingredient_id` 为空，并保留用户确认后的商品名称作为库存占位。

但现有表没有以下能力：上传文件的归属和状态、OCR 原始文本、每条识别结果、匹配置信度、用户在确认页的修改、一次导入产生了哪些库存行、失败重试和重复确认保护。因此不能把小票草稿直接写入 `inventory`，否则用户还没确认的数据会污染真实库存。

##### 2. 建议的数据结构

建议新增以下三张表，并对 `inventory` 做最小扩展。

| 结构 | 作用 | 第一版建议字段 |
|---|---|---|
| `receipt_imports` | 一次上传和识别任务 | `id`、`user_id`、`storage_path`、`source_type`、`file_hash`、`status`、`merchant_name`、`purchased_on`、`raw_text`、`error_message`、`created_at`、`confirmed_at` |
| `receipt_items` | 小票中的一行草稿及用户确认结果 | `id`、`receipt_import_id`、`position`、`raw_line`、`raw_name`、`raw_quantity`、`raw_unit`、`raw_price`、`ingredient_id`、`match_status`、`match_confidence`、`confirmed_name`、`confirmed_quantity`、`confirmed_unit`、`storage`、`action`、`inventory_id` |
| `ingredient_aliases` | 用户确认过的商品名到既有食材的映射 | `id`、`user_id`、`ingredient_id`、`alias`、`normalized_alias`、`created_at` |

`receipt_imports.status` 建议限制为 `uploaded`、`processing`、`ready_for_review`、`confirmed`、`failed`、`cancelled`。`receipt_items.match_status` 建议限制为 `matched`、`possible_match`、`unmatched`、`ignored`。`action` 建议限制为 `add_to_inventory`、`ignore`。

`inventory` 建议增加 `receipt_item_id`，并为它建立唯一约束。这样一条小票条目最多只能生成一条库存记录，确认请求重试时也不会重复入库。是否需要额外的 `display_name` 字段需要产品确认：已匹配条目可显示 `ingredients.name`，未匹配库存占位则需要显示用户确认后的名称，现有 `receipt_raw_name` 的语义不足以同时表达“原始识别名称”和“确认后的展示名称”。

##### 3. OCR/AI 的放置方案

有三种路径：

1. 手动 mock：前端或数据库预先生成草稿。它适合验证确认页交互，不提供真实识别能力。
2. 浏览器直接调用外部 OCR/AI：实现最短，但密钥会暴露给客户端，且难以统一鉴权、限额和错误处理，不建议采用。
3. Supabase Edge Function 调用外部 OCR/AI：推荐。浏览器只上传私有文件并调用受登录保护的 `process_receipt`；函数验证文件归属后，使用服务器端密钥调用外部识别服务，再写入草稿表。

建议分两步推进：先用手动 mock 验证前端确认流程；获得 `approved` 后，再实现“私有 Storage + Edge Function + 外部 OCR/AI”。Edge Function 是调用和保护密钥的位置，OCR/视觉识别本身仍由外部服务完成。

##### 4. RLS、图片和用户隔离

小票包含购买信息，原图必须放在私有 Storage bucket，例如 `receipt-source`，对象路径固定为 `{user_id}/{receipt_import_id}/original`。不使用公开 bucket 或公开 URL。

Storage policy 只允许已登录用户读取、上传和删除自己用户 ID 文件夹中的对象，并限制允许的 MIME 类型与文件大小。第一版建议先限定 JPEG、PNG 和 WebP；是否支持 PDF 要在产品范围确认后再加入，因为外部识别服务对 PDF 的能力不同。

`receipt_imports` 使用与现有用户表相同的直接 `user_id = auth.uid()` RLS。`receipt_items` 的所有策略通过所属 `receipt_imports.user_id = auth.uid()` 验证。`ingredient_aliases` 同样按 `user_id` 隔离。

Edge Function 必须验证调用者 JWT，并验证传入 `receipt_import_id` 属于该用户。若函数使用 service role 写入草稿，必须从已验证的 JWT 获取用户 ID，不能信任客户端传来的 `user_id`。外部 OCR/AI 密钥只存放在 Edge Function 的服务器端环境变量中，不进入前端环境变量或仓库。

##### 5. 确认入库、重复保护和撤销

确认入库必须是一个 RPC，例如 `confirm_receipt_import(import_id, items)`，在单一数据库事务中完成：锁定导入记录、验证归属与状态、验证提交的条目属于该导入、插入或更新库存、写回每条 `inventory_id`、将导入改为 `confirmed`。任何一步失败时，全部回滚。

重复保护至少需要两层：`receipt_imports` 以 `(user_id, file_hash)` 提示同一文件已经上传；`inventory.receipt_item_id` 的唯一约束阻止同一条目重复入库。RPC 对已经 `confirmed` 的导入应返回既有结果，而不是再次写入。

第一版不建议承诺“任意时刻一键撤销”。草稿阶段可以直接取消。确认后应保留导入历史和条目到库存的链接。若后续库存会被做饭或手工修改，可靠撤销需要新增库存流水表，不能简单删除库存行。第一版可先把“撤销已确认导入”列为下一期能力，或仅允许在所有关联库存行未被后续修改时撤销。这一范围需要产品主对话确认。

##### 6. 获得批准后需要写入数据契约的内容

当前 `docs/data-contract.md` 只覆盖第一版记餐链路，厨房和库存仍是占位页，因此现在不应把上述接口标记为“已支持”。获得批准并完成迁移后，至少需要新增：

1. `ReceiptImportStatus`、`ReceiptItemMatchStatus`、`ReceiptImport`、`ReceiptItem` 和库存展示行的数据类型。
2. 创建导入、读取草稿、更新草稿条目、确认入库、取消草稿的 RPC 或 Edge Function 调用方式、入参和返回值。
3. 文件上传约束：支持的格式、大小上限、私有 bucket 规则和失败状态。
4. 匹配规则：别名匹配、推荐匹配、人工选择与未匹配库存占位的边界。
5. 幂等和错误语义：重复文件、识别失败、确认失败和已确认导入重试时的前端行为。

##### 第一版后端范围

实现私有图片上传、识别草稿、人工确认、写入库存、别名匹配和防重复确认。暂不承诺 PDF、自动创建 `ingredients`、营养标签拍照、单品选择器扩展、复杂撤销或跨用户共享食材库。

#### 后端实现与远端验证

已部署并验证以下能力：

1. 私有 `receipt-source` 图片桶只允许上传 JPEG、PNG、WebP，单张最多 10 MB。对象必须关联当前用户已创建的导入任务，不能使用公开 URL。
2. `create_receipt_import` 创建上传任务并返回固定路径。`get_receipt_import`、`list_receipt_imports`、`update_receipt_items` 提供草稿读取和人工确认修改。
3. `receipt_imports`、`receipt_items`、`ingredient_aliases` 和 `inventory.receipt_item_id` 已迁移到远端。匹配结果先写草稿。确认后才创建库存批次和 `purchase` 流水。
4. `confirm_receipt_import` 是单一事务，使用幂等键。相同键和相同确认内容返回第一次结果。相同键用于另一张小票返回 `IDEMPOTENCY_CONFLICT`。任意验证失败会回滚整次入库。
5. 匹配规则依次使用用户已确认别名、已有食材标准名和低置信度推荐。用户确认后，已匹配商品会写入别名。未匹配商品保留为空的 `ingredient_id`，作为库存占位。
6. `search_cook_inventory` 已返回未匹配库存。`save_cook_session` 增加可选 `p_unmatched_items`，按原量词扣库存并写入 `cook_unmatched_items`，但不写入营养用的 `cook_items`，所以不会进入单品选择器。
7. `process-receipt` Edge Function 已部署，并已接入 Azure Document Intelligence `prebuilt-receipt`。它验证登录、导入归属和私有原图存在后才发送识别副本。Azure endpoint 与 key 只保存在 Supabase Secrets。9.49 MB 真实小票已远端返回 13 条商品行并进入 `ready_for_review`。
8. 已增加可选的服务端 AI 商品匹配建议。Azure 继续负责商品行识别，OpenAI 只接收商品名称和当前用户已有食材目录。AI 候选保存在独立建议字段中，不能直接成为已确认食材、库存或别名。生产环境尚未配置 `OPENAI_API_KEY`，因此当前不会调用 OpenAI，也不会产生相关费用；Azure OCR 和人工搜索会按原路径继续工作。

#### 轻量确认页契约补充

本轮比较了三种数量和量词方案。

1. 所有识别结果统一写为 `1 件`。它最安全，但会丢失 OCR 同时识别到可靠数量和单位的情况。
2. 只有数量与单位同时可信时保留 OCR 结果。其余情况由后端生成 `1 件` 草稿。已采用。
3. 允许库存数量或单位为空。它会破坏现有库存扣减和流水约束，因此不采用。

后端已完成最小契约修正并部署。价格字段与数量字段保持分离。无量词的数字和与价格相同的数字只保存在 OCR 原始证据中，不进入 `confirmedQuantity`。安全默认值固定为 `confirmedQuantity = 1`、`confirmedUnit = '件'`。这里的“件”只表示一个通用库存项目，不代表克重、盒数或营养份量。

用户省略量词时，`update_receipt_items` 也由后端使用同一默认值，前端不需要猜测“盒、把、袋”等量词。名称仍需存在。存放位置必须从 `常温`、`冷藏`、`冷冻` 中选择。提交错误以稳定错误码返回，`error.details` 同时包含 `receiptItemId` 和字段名，供前端在对应卡片内显示。

商品匹配继续采用三层规则。用户以前确认过的完整别名可以自动匹配。已有食材完整同名可以自动匹配。包含关系或模糊结果只能是 `possible_match`，必须由用户确认。普通酸奶、无糖酸奶、低脂牛奶、高钙牛奶等名称只要不是完整同名或已经确认的完整别名，就不能通过泛化名称自动进入可靠营养计算。

新增只读 `search_receipt_ingredients`，让确认页可以搜索当前用户的已有食材。用户把 `CHIQ BANANAS`、`BACC BANANAS` 或其他完整商品名分别确认到 `香蕉` 后，每个完整名称都会保存为独立别名，并可在后续导入中自动复用。同一商品第一次出现时仍需人工确认。配置服务端 AI 后，跨语言名称可以得到待确认建议，但不能自动写入可靠营养匹配。

远端隔离测试已通过安全默认值、可靠数量保留、敏感规格降级为可能匹配、字段级错误、食材搜索、别名创建与复用、确认幂等、跨用户隔离和三值库存位置约束。测试账号和测试数据已清理。

#### OCR 服务接入选型信息

当前 `process-receipt` 已直接接入 Azure Document Intelligence。`RECEIPT_OCR_URL` 保存 Azure resource endpoint，`RECEIPT_OCR_API_KEY` 保存 Azure Key1。两项都通过 Supabase Secrets 配置，不进入前端环境变量或仓库。

浏览器调用 Edge Function 时会发送：

```json
{
  "receiptImportId": "...",
  "imageBase64": "...",
  "imageContentType": "image/jpeg"
}
```

`imageBase64` 是浏览器本地生成的临时识别副本。原图仍保存在私有 Storage。Edge Function 不信任副本中的用户信息，只使用已验证 JWT 对应的导入任务。它使用 `Ocp-Apim-Subscription-Key` 在服务器端调用 Azure，轮询分析结果并映射为统一草稿：

```json
{
  "rawText": "完整识别文本",
  "items": [
    {
      "name": "商品名称",
      "line": "原始商品行",
      "quantity": 1,
      "unit": "盒",
      "price": 4.99
    }
  ]
}
```

`quantity`、`unit` 和 `price` 允许为空。前端确认入库前仍必须让用户补齐名称、正数数量和量词。OCR 结果只生成建议，不能直接写库存。

#### 最终决定与原因

已确认采用“库存优先，不直接生成可记餐单品”。

第一版只做照片小票导入、识别小票商品行、匹配已有食材、人工确认和写入库存。PDF 导入暂缓。未匹配商品允许进入库存，也允许用于做饭，但在补充 Nutrition Facts Label 前不进入单品选择器，不作为可靠单品营养来源。

第二版再做营养标签拍照、自动建食材、补齐标准份量，并让补齐后的商品进入单品选择器。

#### 验收标准

第一版验收标准：

1. 用户可以从厨房首页的“添加冰箱库存”进入照片小票导入。
2. 上传后系统生成一次小票导入草稿，并展示识别到的商品行。
3. 每一行可以呈现已匹配、可能匹配、未匹配、忽略等状态。
4. 已匹配商品写入库存时关联已有 `ingredients`。
5. 未匹配商品可以作为库存占位写入库存，并保留原始小票名称和用户确认后的展示名称。
6. 未匹配库存可以在做饭流程中被选用，但不能进入单品选择器。
7. 已匹配且已有标准份量的食材，可以继续通过现有单品选择器逻辑出现。
8. 同一小票条目重复确认不会重复写入库存。
9. 跨用户不能读取、确认或写入他人的小票、草稿、库存或别名。
10. PDF、营养标签拍照、自动建食材和单品选择器扩展不作为第一版验收项。

### FR-002 · 第一版扩展为记录 / 厨房 / 采购最小闭环

**状态：** `frontend_connected`
**提出位置：** 产品主对话
**当前负责人：** 产品主对话验收
**最后更新：** 2026-07-13

#### 原始想法

记录、厨房、采购是环环相扣的。没有库存就无法记成品；没有下厨做菜，也就没有成品可以进入记录。因此厨房和采购必须做好，才能继续做真实产品测试。前端下一步需要根据 Figma 里的高保真，把厨房和采购的所有页面做好。

#### 希望解决的问题

当前第一版记录链路已经完成前后端真实联调，但它只能验证技术链路，不能验证用户真实使用路径。真实产品闭环应当是：先采购，形成库存；再在厨房做饭，生成成品；最后在记录里吃掉这些成品。若厨房和采购只保留占位页，阶段 1 主流程测试无法代表实际使用。

#### 产品流程草案

```text
采购
→ 心愿单 / 候选菜池
→ 本周食谱预览和调整
→ 生成采购清单
→ 采购完成
→ 厨房库存
→ 选择本周食谱中的菜
→ 做饭主流程
→ 选择食材并确认本次用量
→ 保存成品
→ 记录页新建一餐
→ 从成品选择器选择已做好的成品
→ 保存一餐
→ 今日页看到更新后的营养数据
```

当前判断是：记录链路技术联调完成，但产品验收不能只停在记录链路。第一版产品范围需要扩展为“记录 / 厨房 / 采购最小闭环”。

#### 当前尚未确认的问题

1. Figma 中厨房和采购哪些高保真页面已经是最终稿，哪些仍是探索稿或低保真。
2. 厨房首页、库存列表、做饭、食材选择器、保存成品、采购候选菜池、下周食谱、编辑食谱和采购清单各自需要哪些真实数据。
3. 现有数据库里的 `recipes`、`recipe_items`、`cook_sessions`、`cook_items` 和空的 `inventory` 能支持哪些厨房页面。
4. 采购的心愿单、候选菜池、随机抽取、下周食谱和采购清单目前没有数据契约，需要判断第一版如何处理。
5. 前端能否先实现页面骨架和交互，但把没有后端契约的部分明确标注为待接入，而不是表现成真实功能。
6. 第一版是否允许没有真实库存扣减，只完成“做饭生成成品 → 记录吃成品”的最小闭环。
7. FR-001 小票导入与本需求的边界。小票仍为 `needs_review`，不能混入本轮正式实现。
8. 阶段 1 产品测试清单需要如何调整，才能覆盖采购、厨房和记录的完整路径。

#### 候选方案

**方案 A：扩展第一版为记录 / 厨房 / 采购最小闭环，当前选择。**
前端根据 Figma 高保真评估并实现厨房和采购页面，产品验收按真实使用链路推进。优点是符合实际使用方式。风险是数据契约和后端能力尚未补齐，需要先评估再实现。

**方案 B：只验收记录链路。**
维持现有第一版范围，只把记录作为技术 demo 验收。优点是当前已经基本可测。缺点是无法代表真实产品使用，因为成品来源缺失。

**方案 C：先只补厨房，不补采购。**
先让“做饭生成成品 → 记录吃成品”闭环成立。优点是范围比方案 A 小。缺点是仍缺少采购到库存的前置链路，和用户当前判断不一致。

当前产品决定采用方案 A。前端评估已完成，下一步进入后端评估。

##### 3. 厨房状态要求

1. 加载状态。首页、库存、做饭准备和食材选择器分别显示与页面结构一致的骨架。加载期间不显示设计样例。
2. 空库存。显示明确空状态，并提供前往采购的入口。FR-001 未批准前不提供可用的小票导入入口。
3. 无本周食谱。隐藏菜谱卡片样例，显示前往采购规划的入口。
4. 食材不足。缺少项和可用量必须来自后端结果。前端不能仅根据字符串单位自行换算。是否允许继续做饭由产品和后端契约共同确定。
5. 保存中。禁用保存和返回后可能造成重复提交的操作，并阻止连续点击。
6. 保存失败。保留成品名称、份数、食材、用量和来源草稿。网络失败不自动重试，只允许用户手动重试。
7. 保存成功。只使用后端返回的真实成品标识和数据。随后重新读取厨房首页，并使记录页成品选择器重新请求真实列表。

##### 4. 采购状态要求

1. 候选菜池为空。显示空状态和候选来源说明，不渲染样例卡片。
2. 随机抽取中。锁定重复抽取和确认操作。成功结果必须来自后端。
3. 无可生成采购清单。明确说明是没有已确认食谱，还是食谱缺少可计算的食材。原因必须由后端返回。
4. 编辑未保存。周计划在前端维护草稿和 `dirty` 状态。离开页面前需要二次确认。保存失败后保留全部修改。
5. 生成失败。保留已确认或正在编辑的周计划，并提供手动重试。
6. 复制成功。复制动作可以由浏览器 Clipboard API 完成，并显示短暂成功提示。浏览器拒绝权限时显示复制失败，不能误报成功。

##### 5. 未就绪能力的前端处理

页面数据必须通过独立适配层进入组件。适配层只有四类可见结果：加载、真实数据、真实空结果和明确的未就绪或错误。设计样例只能存在于 Figma、测试 fixture 或组件开发环境中，不能作为生产默认值。

FR-002 获得 `approved` 但后端尚未 `backend_ready` 时，可以实现路由、视觉骨架和纯本地草稿交互，但入口仍需标明未开放，所有会改变真实数据的操作必须禁用。不能出现假的随机成功、生成成功、采购完成、库存更新或成品保存成功。

##### 6. 保存成品与记录选择器的衔接

厨房保存必须由后端在一个事务中创建真实 `cook_sessions` 和对应 `cook_items`。保存成功后，前端清空厨房草稿并重新请求厨房数据。记录页成品选择器继续只调用已支持的 `search_meal_components(p_source_type: 'cook_session')`。该 RPC 已限定只返回仍有剩余份数的真实成品，因此新成品在保存事务完成后会通过下一次请求自然出现。

前端不能把刚保存的本地对象直接插入成品选择器来代替远端结果。若保存成功后搜索结果暂时未出现，应显示重新加载状态并允许手动重试。

##### 7. 第一版范围与工作量

有三种前端范围可供产品确认：

1. **真实数据闭环。建议采用。** 采购完成写入库存；做饭保存同时生成成品并按已确认规则扣减库存；记录选择器读取新成品。它能验证页面、交互和数据正确性。
2. **交互闭环。** 采购完成写入库存，做饭生成成品，但不扣减库存。它可以测试主流程，但连续使用后库存会失真，不能作为数据正确性验收范围。
3. **视觉原型。** 只完成页面和本地草稿，所有保存动作保持未就绪。它只适合设计可用性测试，不能替代真实产品验收。

前端建议选择第 1 种。理由是本轮目标包含“data 是否显示完整正确”。若做饭后库存不变化，同一批库存可以被重复使用，厨房首页和下一次采购清单都会产生错误结果。

现有前端只有记录链路和两个占位页。FR-002 需要新增 9 个范围内页面，扩展路由和跨页草稿，增加厨房与采购适配层，并补齐各页状态和集成测试。整体前端工作量为大型。厨房主流程、采购主流程、数据适配与端到端回归均是独立工作块。在后端确定周计划、库存和单位语义前，不提供天数估算。

后端必须先完成以下前置项，前端才能接入真实能力：

1. 确认候选菜池和本周计划的数据模型及用户隔离方式。
2. 提供采购清单生成和采购完成写库存的事务能力。
3. 提供库存读取、修改、状态计算和做饭扣减规则。
4. 提供做饭准备数据和保存成品的事务能力。
5. 定义所有写操作的重复请求、回滚、权限和错误语义。
6. 提供可用于加载、空、错误、食材不足和保存失败验证的测试数据。

##### 8. 需要新增到 `data-contract.md` 的数据需求

以下仅记录前端需要的能力，不预设表名、字段名、RPC 名或 View 名。由后端评估后确定技术形式，并在验证完成前保持“未支持”。

1. 厨房首页返回结构。需要库存摘要、本周食谱、已做好成品及稳定标识。
2. 库存展示结构。需要食材标识、名称、数量、单位、存放位置、低量或临期状态，以及状态的后端计算规则。Figma 中“2 天内”需要到期信息或等价的后端结果，现有契约未定义。
3. 周计划结构。需要计划周期、日期或星期、食谱标识、来源、顺序和保存状态。
4. 候选菜池结构。需要食谱标识及“想吃、候选、保留、跳过”等产品确认后的状态语义。
5. 采购清单结构。需要分组、食材标识、名称、合并后数量、单位、库存抵扣结果和是否完成。
6. 做饭准备结构。需要食谱、参考食材、计划用量、库存可用量、缺少原因和可编辑范围。
7. 保存成品输入和结果。需要成品名称、总份数、食材及实际用量、来源食谱、真实 `cook_session` 标识和营养结果。
8. 库存写入与扣减能力。采购完成和保存成品都需要单一事务、完整回滚和重复请求保护。
9. 周计划随机抽取、编辑保存、采购清单生成、采购完成、库存读取更新、做饭准备和保存成品的页面级调用契约。
10. 权限、无效引用、数量或单位冲突、库存不足、重复提交和网络失败的错误码及前端处理规则。

#### 后端评估

**结论：** 现有表已能保存食谱、食谱参考用量、实际成品和成品营养，也能让新成品在保存后通过已支持的 `search_meal_components('cook_session', ...)` 出现在记餐选择器中。但它们不能独立保证采购入库、库存扣减、周计划和采购清单的数据正确性。FR-002 需要新增库存流水、候选菜池、周计划和采购清单的数据结构，并以事务 RPC 完成两次真实写入。此处只是评估，不实施迁移，也不修改 `docs/data-contract.md`。

##### 1. 现有表的支持边界

| 现有结构 | 可以支持 | 不能支持或需要补充 |
|---|---|---|
| `recipes`、`recipe_items`、`recipe_nutrition` | 食谱卡片、参考食材和以克为单位的参考营养 | 候选状态、排期、采购状态，以及库存是否足够 |
| `cook_sessions`、`cook_items`、`cook_nutrition` | 保存后的真实成品、实际营养和记餐成品选择器 | 与库存批次的扣减关联、重复保存保护和失败回滚入口 |
| `inventory` | 每位用户的一条库存记录，含数量、单位、存放位置和购买日期 | 批次来源、可用量变化、到期、单位规则、扣减历史、低量判断和并发安全 |
| 现有记餐 RPC | 成品保存后可继续被记餐，剩余成品份数由已吃份数计算 | 不能改作厨房选择器，也不能承担采购或做饭写入 |

`inventory` 当前没有数量正数约束、受控单位、流水、时间戳或与 `cook_sessions` 的关联。因此直接让前端插入、修改或减少它，无法判断一次采购或一次做饭到底改变了什么，也无法可靠撤销或处理并发。厨房库存选择器必须新增独立读取契约，不能复用记餐选择器。

##### 2. 建议的数据模型

建议保留 `inventory` 作为当前库存批次，并只做必要扩展：`display_name`、`available_quantity`、`unit_kind`、`expires_on`、`created_at`、`updated_at` 和来源标识。已匹配食材的行必须有 `ingredient_id`。未匹配库存占位仍属于 FR-001，不作为本需求的正式能力。

建议新增 `inventory_movements` 作为不可修改的库存流水。每条流水记录库存批次、用户、变化类型、数量变化、单位、关联业务对象和发生时间。变化类型至少包含 `purchase`、`cook_consumption`、`adjustment` 和未来可用的 `reversal`。购买完成写正数流水，保存成品写负数流水。库存当前可用量由事务同步维护；流水用于追溯和撤销判断。

建议新增 `recipe_candidates`。它保存用户、食谱、状态和排序。状态候选为 `wanted`、`candidate`、`kept`、`skipped`。随机抽取规则目前没有产品定义，不能在后端自行设定。

建议新增 `weekly_plans` 和 `weekly_plan_items`。前者保存用户、周起始日、状态和时间戳。后者保存计划、日期或星期、食谱、计划份数、顺序和来源。候选菜池只提供可选食谱，周计划才是采购清单的确定输入。

采购清单有两种可选模型：

1. 仅用 RPC 从已确认周计划、`recipe_items` 和库存实时计算。它适合只读清单。
2. 新增 `shopping_lists` 和 `shopping_list_items`，把生成时的需求量、库存抵扣、用户调整和完成状态保存为快照。推荐此方案，因为“采购完成”需要对应一份确定清单，计划或库存后来变化时也不会改变已完成采购的依据。

推荐采用第 2 种。清单条目必须同时保存食材标识、显示名称、需要量、单位、库存可覆盖量、待购量和完成数量。不能把不同单位自动合并。

##### 3. 单位、数量与营养语义

库存数量和营养克重是两类数据。手动库存只允许用户记录明确的数量与量词，例如 `1 个`、`1 盒`、`1 把`、`1 碗`。前端不能把它们自行换算为克。

`recipe_items.grams` 和 `cook_items.grams` 仍是营养计算使用的克重。克重只能来自小票、营养来源或已有的标准份量。库存批次只有在存在可信克重来源或与扣减量使用完全相同单位时，才能参加自动库存扣减。

这意味着需要在产品实现前确认一条规则：一盒或一把这类没有可信克重的库存，是否允许以相同量词和用户确认的分数扣减。若允许，库存流水只记录同单位的数量变化，不把它推算为克。若不允许，这类库存可以展示，但不能用于“库存足够”的自动判断。两种规则都会影响做饭准备页的可编辑范围，因此不能由前端临时决定。

##### 4. 两个写入事务

**采购完成 `complete_purchase`。** RPC 必须验证登录用户、采购清单归属和状态，再锁定清单及条目。它写入或增加对应库存批次、写入 `purchase` 流水、回写每个清单条目的完成数量，并将清单改为已完成。任一条目无效、数量不合法或写入失败时，整个采购不生效。

**保存成品 `save_cook_session`。** RPC 必须验证来源食谱、全部食材、总份数和营养克重，再按稳定顺序锁定所选库存批次。确认每条库存归当前用户、单位可比较、扣减量大于零且扣减后不小于零。随后在同一事务内创建 `cook_sessions`、创建全部 `cook_items`、写入全部 `cook_consumption` 流水并更新库存可用量。提交成功后，现有成品选择器即可读取真实成品。任何一步失败时，成品、库存和流水全部回滚。

两种写入都需要幂等键。建议新增通用 `operation_requests`，至少保存用户、操作类型、客户端幂等键、请求摘要、结果对象和创建时间，并对“用户加操作类型加幂等键”设唯一约束。相同键且相同请求返回第一次成功结果，不再次扣库存或创建成品。相同键但请求不同返回 `IDEMPOTENCY_CONFLICT`。网络中断时，前端必须用同一个键查询或重试，不能生成新键后盲目再提交。

当前不把“删除已保存成品并自动退回库存”纳入 FR-002。若以后需要撤销，必须先判断该成品是否已经被记餐；只有未被消费的成品才可能通过新增反向流水安全撤销。

##### 5. 页面级调用契约建议

以下名称只是评估用候选，尚未写入数据契约，也未实现。

| 页面 | 需要的读取或写入能力 |
|---|---|
| 厨房首页 | `get_kitchen_home` 返回库存摘要、已排期食谱和可食用成品 |
| 库存列表 | `list_inventory` 返回批次、食材、可用数量、单位、存放位置、到期和后端计算状态 |
| 做饭准备 | `get_cook_preparation(recipe_id, plan_item_id?)` 返回食谱参考量、可选库存批次、短缺项和不可自动换算原因 |
| 食材选择器 | `search_cook_inventory(query)` 只返回当前用户库存及其单位、可用量和可扣减状态 |
| 保存成品 | `save_cook_session(idempotency_key, payload)` 返回真实成品、营养、扣减结果和库存摘要 |
| 候选菜池 | `list_recipe_candidates` 与 `set_recipe_candidate_status` |
| 周计划预览与编辑 | `get_weekly_plan` 与 `save_weekly_plan`。随机抽取接口要等抽取规则确认后再定义 |
| 采购清单 | `generate_shopping_list`、`get_shopping_list` 和 `complete_purchase` |

所有读取都必须返回真实空结果和可区分的业务错误。前端的加载状态由请求过程表现，不能用设计样例代替。

##### 6. RLS 与用户隔离

每张新增主表都保存 `user_id`，并启用 RLS。子表必须通过父表归属验证访问权限，例如计划条目通过周计划、清单条目通过采购清单、库存流水通过库存批次。所有 RPC 使用 `security invoker`，从 `auth.uid()` 取用户，绝不接受客户端传入的用户 ID。

库存余额、库存流水、采购完成和保存成品应只允许 RPC 写入。直接表写入权限需要收紧，避免客户端绕过锁定、库存不足检查和幂等保护。新增 View 也必须使用 `security_invoker`。跨用户的食谱、库存批次、计划、清单、成品和流水引用一律视为无效引用，不能返回其存在与否的额外信息。

##### 7. 错误语义

新增写入 RPC 应返回稳定业务码。具体错误文本可变，前端以业务码决定界面行为。

| 场景 | 建议业务码 | 后端结果与前端行为 |
|---|---|---|
| 未登录 | `AUTH_REQUIRED` | 不写入，前端回登录页 |
| 不存在或跨用户引用 | `INVALID_REFERENCE` | 不透露对方数据，不写入，前端重新加载选择器或计划 |
| 数量不合法 | `QUANTITY_INVALID` | 不写入，保留草稿并标出对应条目 |
| 单位不一致或缺少可信换算 | `UNIT_CONFLICT` | 不推算克重，不写入，要求用户选择可比较库存或确认规则 |
| 库存不足 | `INSUFFICIENT_STOCK` | 返回短缺食材和可用量，整次保存成品回滚 |
| 清单或计划状态冲突 | `CONFLICT` | 不写入，前端重新读取后决定是否重试 |
| 重复请求 | `IDEMPOTENCY_CONFLICT` 或既有成功结果 | 同键同请求返回旧结果；同键不同请求提示冲突 |
| RLS 或权限失败 | `FORBIDDEN` | 不显示匿名数据，登录失效时回登录页 |
| 网络失败 | `NETWORK_UNKNOWN` | 数据库结果可能未知，保留草稿，使用原幂等键查询或手动重试 |

##### 8. 需要补充的测试数据和验证

需要至少两个隔离测试账号。空账号用于验证空库存、空候选池、空周计划和无可生成采购清单。完整账号需要：有可信克重来源的食材、有仅量词库存的食材、一项库存不足食材、至少两份食谱、候选状态、已确认周计划和一份可完成采购清单。

验证必须覆盖：采购完成后库存与流水一致；保存成品后库存减少、`cook_sessions` 和 `cook_items` 同时出现，且成品选择器可读；任何中途失败都没有部分写入；库存不足和单位冲突不产生新成品；同一幂等键不会重复采购或扣库存；跨用户引用被拒绝；空状态和真实加载、网络失败的前端处理可被复现。低量、临期和随机候选池的计算规则尚未确认，不能先制造“正确”的测试预期。

##### 9. 后续应进入数据契约的内容

产品确认模型并完成迁移和验证后，`docs/data-contract.md` 才应增加厨房、库存、候选菜池、周计划、采购清单、做饭准备、保存成品和采购完成的类型、入参、返回值、RLS 边界、单位规则、幂等规则和错误码。每项只有在远端验证通过后才能标为“已支持”。

以下仍保持未支持：随机抽取的具体规则、低量阈值、临期规则、替代食材、不同单位换算、库存手工调整和撤销已做成品。它们需要产品进一步确认。

小票导入、OCR、PDF、营养标签识别、库存导入历史、私有图片存储和别名匹配继续属于 FR-001。本次评估不会把它们作为采购完成的输入或实现内容。

#### 最终决定与原因

已批准后端进入 FR-002 实现。第一版目标采用“真实数据闭环”：采购完成写入库存；保存成品时扣减库存并创建真实 `cook_sessions`；记录选择器继续通过已支持的 `search_meal_components(p_source_type: 'cook_session')` 读取真实成品。

后端实现采用评估中的推荐模型：保留并扩展 `inventory` 作为库存批次；新增不可修改的 `inventory_movements` 记录库存流水；新增 `recipe_candidates`、`weekly_plans`、`weekly_plan_items`、`shopping_lists`、`shopping_list_items` 和 `operation_requests`；所有真实写入通过 RPC 事务完成。

单位规则按产品当前决定执行：没有可信克重的库存允许按相同量词扣减，例如 `1 盒` 扣 `0.5 盒`。这类扣减只记录同单位数量变化，不换算成克。克重只能来自小票、营养来源、已有标准份量或后端已确认的营养数据。后端需要把库存扣减数量和营养计算克重分开建模，前端不能自行把 `个`、`盒`、`把`、`碗` 推算为克。

随机抽取只做第一版最小能力：从用户候选菜池中抽取可用食谱，具体推荐算法、低量阈值、临期规则、替代食材、不同单位换算、库存手工调整和撤销已做成品都不进入 FR-002 第一版。

第一版周计划文案和数据口径统一为“本周”。前端使用当前自然周周一作为采购计划起点，并与 `get_kitchen_home` 读取的当前自然周保持一致。第一版不增加周选择，也不使用“下周”作为正式页面文案。

FR-001 继续保持独立。小票导入、OCR、PDF、营养标签识别、库存导入历史、私有图片存储和别名匹配不进入本轮后端实现。

#### 验收标准

后端实现完成后需要满足：

1. 远端数据库完成必要迁移，并通过 RLS 验证用户隔离。
2. `inventory`、库存流水、候选菜池、周计划、采购清单和幂等请求模型可以支撑 FR-002 的 9 个页面。
3. `complete_purchase` 能在一个事务中完成采购清单校验、库存批次写入或增加、`purchase` 流水写入、清单状态更新和完整回滚。
4. `save_cook_session` 能在一个事务中完成来源验证、库存锁定、库存扣减、`cook_sessions` / `cook_items` 创建、`cook_consumption` 流水写入和完整回滚。
5. 两个写入事务都有幂等键。同键同请求返回第一次成功结果，不重复入库、不重复扣库存、不重复创建成品。同键不同请求返回稳定冲突错误。

7. 错误码覆盖未登录、无效引用、数量不合法、单位冲突、库存不足、状态冲突、重复请求、权限失败和网络结果未知。
8. 测试数据覆盖空账号、完整账号、可信克重库存、仅量词库存、库存不足、空周计划、可完成采购清单、保存成品成功和失败回滚。
9. 验证完成后更新 `docs/data-contract.md`，只把远端已验证通过的契约标为“已支持”。
10. 后端完成并验证前，前端仍不得把厨房和采购表现为真实已支持能力。

### FR-003 · 粘贴解析并添加菜谱到候选池

**状态：** `approved`
**提出位置：** 产品主对话
**当前负责人：** 当前后端对话
**最后更新：** 2026-07-15

#### 原始想法

采购流程新增“添加菜谱”页面。用户输入菜名、食材、数量和单位，保存后加入候选菜池。页面还探索了直接加入本周和粘贴文本解析。

#### 希望解决的问题

当前候选菜池只能读取已经存在并已加入 `recipe_candidates` 的食谱。用户无法从正式界面创建自己的菜谱，因此候选菜池为空时缺少真实的数据入口。

逐行手动录入不是第一版主场景。目标路径是“粘贴完整菜谱文本 → 得到可编辑解析草稿 → 确认食材和克重 → 真实保存到候选菜池”。

#### 当前尚未确认的问题

三个最小范围问题已经由产品主对话确认。后端实现完成并远端验证后，FR-003 可以进入 `backend_ready`。

#### 候选方案

解析位置有三种方案：

1. **前端本地规则。** 不产生模型费用，适合“牛肉 500g”一类整齐文本。它无法稳定处理网页复制正文、自然语言步骤、混合单位和省略写法，不能单独承担第一版主入口。
2. **数据库 RPC 解析。** PostgreSQL 适合校验、匹配和事务写入，不适合自然语言结构化，也不应直接管理外部模型请求。
3. **Edge Function 调用 AI，数据库 RPC 负责匹配和保存。推荐。** Edge Function 验证用户、限制文本长度、保护模型密钥并返回统一 JSON。前端可以先用本地规则做即时拆行，但 AI 输出仍只进入可编辑草稿。数据库继续负责食材归属、克重规则、RLS、幂等和原子写入。

FR-003 继续保持独立，不并入已经 `frontend_connected` 的 FR-002。

#### 前端评估

产品确认后，第一版默认入口调整为“粘贴解析”。粘贴区位于页面主视觉位置。当前前端只做确定性的本地初步拆行：每个非空行生成一条可编辑食材，保留原文，不猜测菜名、数量、量词或食材匹配。生成后用户可以修改名称、数量和量词，也可以手动补充或删除食材。

“手动新建”降级为“手动修正”，用于修正解析结果或补充漏项。页面不再显示“草稿”或“未开放”。第一版加入位置固定表现为候选菜池，不提前提供直接加入本周。当前没有服务端解析和真实保存契约，因此保存按钮继续禁用，并明确说明当前内容只存在于本页面。前端不会直接写 `recipes`、`recipe_items` 或 `recipe_candidates`。

#### 后端评估

现有 `recipes` 已有用户归属和 RLS。`recipe_items` 的读取通过所属 `recipes.user_id` 隔离。当前数据库允许用户直接写入这两张表，并且 `(user_id, name)` 唯一，因此同一用户的完全同名菜谱会被数据库拒绝。

现有能力仍不足以直接支持正式页面：

1. `recipes`、全部 `recipe_items` 和 `recipe_candidates` 需要一次原子写入。当前没有事务 RPC，也没有稳定错误码或幂等键。前端分三步写入时，任一步失败都会留下半成品。
2. `recipe_items` 只有必填的 `ingredient_id` 和 `grams`。它不能保存“2 个”或“1 盒”这类原始数量与单位。
3. `generate_shopping_list`、`recipe_nutrition` 和做饭准备都依赖 `recipe_items.grams`。没有可信克重的自建条目不能直接进入周计划和采购计算。
4. `set_recipe_candidate_status` 只能处理已经存在且属于当前用户的菜谱，不能代替创建菜谱。
5. 当前 `recipe_items` 的插入策略只验证目标菜谱属于当前用户，没有同时验证 `ingredient_id` 也属于当前用户。知道其他用户食材 UUID 的客户端可能建立跨用户引用。正式创建 RPC 必须阻止这种引用，并且应收紧直接表写入权限。

##### 1. 粘贴解析契约

推荐新增受 JWT 保护的 Supabase Edge Function `parse-recipe`。第一版只接收原始文本，不接收客户端传入的用户 ID。建议限制 UTF-8 文本最多 20,000 字符。这个上限是后端方案建议，需要用真实粘贴样本核实。

Edge Function 返回供应商无关的统一草稿：

```json
{
  "suggestedName": "番茄炖牛肉",
  "items": [
    {
      "position": 0,
      "rawText": "牛肉 500g",
      "name": "牛肉",
      "quantity": 500,
      "unit": "g",
      "normalizedGrams": 500,
      "confidence": "high",
      "requiresConfirmation": false
    }
  ]
}
```

解析结果不写入 `recipes` 或 `recipe_items`。前端必须先显示并允许编辑。Edge Function 不创建食材、不推断营养，也不能把非克单位猜成克重。

为减少费用，前端可以先用确定性规则处理标准食材行。无法可靠拆分的文本再调用 Edge Function。服务端需要单用户频率限制，并可以按“用户加文本摘要”短期复用成功结果。是否新增解析缓存表应在选择 AI 服务后确定。

##### 2. 数量、单位和确认状态

正式菜谱仍使用 `recipe_items.grams` 参与营养、做饭准备和采购清单。第一版推荐保持这一约束，不修改 FR-002 的克重计算模型。

1. `g` 直接写入 `normalizedGrams`。
2. `kg` 和 `mg` 使用确定性换算得到克重。
3. `1个`、`半盒`、`一把`、`少许`、`适量` 和体积单位保留原始数量与单位，但 `normalizedGrams` 为 `null`，状态为 `grams_required`。
4. AI 不得利用常识、营养数据或 `serving_grams` 猜测克重。用户补充正数克重后，条目才满足保存条件。

解析草稿只存在于前端状态或受控解析缓存，不需要把 `recipe_items.grams` 改为空。这样不会让无法计算的菜谱进入候选池、周计划或采购清单。

##### 3. 食材匹配与搜索

正式保存的每个条目必须匹配当前用户已有 `ingredients`。解析出的名称先做完整同名匹配。模糊结果只作为 `possible_match`，不能自动确认。未匹配结果必须由用户搜索并选择已有食材，不能自动创建 `ingredients`。

不建议添加菜谱直接调用名称带有小票语义的 `search_receipt_ingredients`。推荐新增通用 `search_ingredients(p_query, p_limit)`，返回食材 ID、名称、分类、包装说明、标准份量和验证状态。`search_receipt_ingredients` 保持兼容。

批量匹配建议新增只读 `match_recipe_ingredients(p_items jsonb)`。它只返回当前用户的完整同名或可能匹配结果，不写数据，也不暴露跨用户名称和 UUID。

##### 4. 正式保存事务

推荐新增 `create_recipe_with_candidate(name, servings, items, idempotencyKey)`。它从 `auth.uid()` 取得用户，并在一个事务内完成：

```text
验证菜名与同名规则
→ 验证全部 ingredientId 属于当前用户
→ 验证全部 grams > 0
→ 创建 recipes
→ 创建全部 recipe_items
→ 创建 candidate 状态的 recipe_candidates
→ 返回 recipeId、candidateId、name 和 itemCount
```

同键同内容返回第一次结果。同键不同内容返回 `IDEMPOTENCY_CONFLICT`。任一步失败时三类记录全部回滚。网络结果未知时复用现有 `get_operation_result` 查询 `create_recipe` 的结果。

##### 5. 同名和直接加入本周

推荐同名策略为“不覆盖”。当前用户已有标准化同名菜谱时返回 `DUPLICATE_RECIPE_NAME`。第一版不自动覆盖、合并或静默创建副本。用户修改名称后重新提交。这个策略能保护已经被周计划或成品引用的旧菜谱。

“直接加入本周”不进入第一版。现有 `save_weekly_plan` 会替换整周条目。安全追加还需要日期、顺序、计划状态和并发冲突规则，成本不低，而且可能破坏 FR-002。第一版保存成功后只加入候选池，用户再通过现有周计划编辑流程加入本周。

##### 6. 权限、幂等和错误语义

正式实现时收紧 `recipes`、`recipe_items` 和 `recipe_candidates` 的直接写权限。读取 RLS 保留。创建 RPC 必须同时验证目标菜谱和每个 `ingredient_id` 都属于 `auth.uid()`，修复当前 `recipe_items` 插入策略只检查菜谱归属的缺口。

`operation_requests.operation_type` 增加 `create_recipe`。解析请求不复用正式保存的幂等键。解析重试可能产生额外模型调用，因此 Edge Function 需要独立请求摘要、频率限制和可选短期缓存。

建议稳定错误码：

| 环节 | 错误码 | 含义 |
|---|---|---|
| 解析 | `AUTH_REQUIRED` | 未登录 |
| 解析 | `RECIPE_PARSE_INPUT_INVALID` | 文本为空、过长或格式不可接受 |
| 解析 | `RECIPE_PARSE_NOT_CONFIGURED` | AI 服务尚未配置 |
| 解析 | `RECIPE_PARSE_UNAVAILABLE` | 服务暂时不可用 |
| 解析 | `RECIPE_PARSE_RESPONSE_INVALID` | 返回结构不符合统一草稿 |
| 解析 | `RATE_LIMITED` | 超过单用户频率限制 |
| 保存 | `RECIPE_NAME_REQUIRED` | 菜名为空 |
| 保存 | `DUPLICATE_RECIPE_NAME` | 当前用户已有同名菜谱，不覆盖 |
| 保存 | `RECIPE_ITEMS_INVALID` | 条目为空、重复或字段结构错误 |
| 保存 | `INGREDIENT_MATCH_REQUIRED` | 条目尚未确认到已有食材 |
| 保存 | `GRAMS_REQUIRED` | 条目没有正数克重 |

#### 最终决定与原因

产品主对话确认采用独立 FR-003 并先保存到候选菜池。第一版的主要输入方式改为粘贴解析，手动输入只作为解析后的修正和补充。页面删除内部状态词“草稿”，粘贴解析不再表现为未来能力。直接加入本周不进入第一版。

后端采用“前端确定性预处理 + Edge Function AI 结构化 + 数据库匹配和事务保存”。产品已经确认正式保存只允许匹配当前用户已有食材且具有正数克重的主要营养来源。`g` 直接使用，`kg` 和 `mg` 确定性换算。非克单位只进入解析确认。盐、胡椒、酱油、醋、蒜末、香料和水默认忽略。油、糖、芝麻酱等热量明显的调味品默认忽略，用户主动加回并补克重后才保存。

同名菜谱不覆盖，返回 `DUPLICATE_RECIPE_NAME`。AI 解析使用受 JWT 保护的 `parse-recipe` Edge Function。AI 只返回可编辑草稿，不决定 `ingredient_id`，也不写入正式表。正式保存由 `create_recipe_with_candidate` 再次验证并在单一事务内完成。第一版推荐服务端默认限制为每位用户每日 10 次、每月 100 次，单次文本最多 20,000 字符。次数上限属于保守初始值，生产使用一段时间后需要根据真实调用记录核实。

后端标记 `backend_ready` 前，前端只能提供本地初步拆行和可编辑界面，不能显示真实保存成功。

#### 后端实现与远端验证

数据库迁移和 `parse-recipe` Edge Function 已部署。`search_ingredients`、`match_recipe_ingredients`、`create_recipe_with_candidate` 和 `get_operation_result('create_recipe', key)` 已通过远端验证。测试覆盖当前用户食材搜索、完整同名、已确认别名、未匹配、原子创建、相同请求重试、幂等冲突、同名拒绝、缺失克重回滚、跨用户食材拒绝、直接表写入拒绝、解析次数记录、CORS 和 JWT。

正式创建现在只能通过 RPC。`recipes`、`recipe_items` 和 `recipe_candidates` 的直接写权限已移除。创建 RPC 同时验证菜谱归属和每个食材归属，修复了旧 `recipe_items` 插入策略只验证菜谱归属的缺口。

解析服务选择 OpenAI Responses API，默认模型为 `gpt-5-mini`，使用结构化输出、`store: false` 和 `minimal` reasoning。需要 Supabase secret `OPENAI_API_KEY`，可选 `RECIPE_PARSE_MODEL`。当前远端没有 `OPENAI_API_KEY`，因此真实解析稳定返回 `RECIPE_PARSE_NOT_CONFIGURED`，不会产生模型费用，也不会占用解析次数。FR-003 暂不改为 `backend_ready`。配置 key 并用真实粘贴样本验证后再推进状态。

#### 验收标准

第一版建议验收：

1. 粘贴标准克重菜谱后返回菜名、食材、数量和单位草稿，不直接写数据库。
2. 粘贴网页正文或混合自然语言时能提取食材行。无法确认的内容明确标记，不静默丢失。
3. `g`、`kg`、`mg` 得到确定克重。`个`、`盒`、`少许` 等保持待补克重，不能直接保存。
4. 每个条目必须确认到当前用户已有食材。模糊和未匹配项不能自动通过。
5. 用户修改解析结果后，保存事务同时创建菜谱、全部条目和候选记录。
6. 任一步失败全部回滚。同键重试不重复创建。同键不同请求返回冲突。
7. 同名不覆盖已有菜谱。跨用户食材引用返回无效引用。
8. 保存成功后候选菜池真实可见，采购清单仍按克重正确计算。
9. 解析服务未配置、不可用、响应异常、频率限制和网络未知都有明确状态，原始文本和确认内容不会丢失。
10. “直接加入本周”不作为第一版验收项。

### FR-004 · 无菜谱做饭并生成候选菜谱

**状态：** `frontend_connected`
**提出位置：** 产品主对话
**当前负责人：** 产品主对话验收
**最后更新：** 2026-07-16

#### 原始想法

用户希望支持“心血来潮做一锅”的路径。不要求这道菜先存在于本周食谱，也不要求先在采购区添加菜谱。做饭时从库存选食材，填写主要食材克重，保存成品后再补一环菜谱确认。

确认后，这一锅不仅成为可记餐成品，也会反向生成一个菜谱，并进入候选菜池，之后可以被本周食谱抽取或手动加入。

#### 希望解决的问题

当前厨房主流程依赖已有菜谱和本周食谱。若候选菜池为空，或者用户临时做了不属于任何计划的菜，就无法自然进入“做饭 → 成品 → 记餐”的闭环。

这会形成一个使用门槛：必须先有菜谱，才能做饭；但真实使用中，菜谱往往来自已经做过的一锅。

#### 产品流程草案

入口放在厨房首页的“本周食谱”卡片内，不单独新增首页大卡片。

```text
厨房首页
→ 无菜谱做饭
→ 从库存选食材
→ 填主要食材克重
→ 保存成品
→ 菜谱确认
→ 菜谱进入候选菜池
→ 成品进入记餐成品选择器
```

#### Figma 现状

UI 页已新增高保真组：

`无菜谱做饭流程 · 高保真 v1`

包含：

1. `厨房首页 · 高保真 v3 · 库存与无菜谱入口`
2. `厨房 · 库存选食材 · 高保真 v1 · 无菜谱来源`
3. `厨房 · 无菜谱做饭 · 高保真 v1 · 食材克重`
4. `厨房 · 保存成品 · 高保真 v2 · 无菜谱来源`
5. `厨房 · 菜谱确认 · 高保真 v1 · 从本锅生成`

#### 当前尚未确认的问题

1. 后端是否新增独立 RPC，还是扩展现有 `save_cook_session`。
2. 保存成品和生成候选菜谱是否必须同一事务完成，还是分两步完成。
3. 若成品保存成功但菜谱确认失败，前端应如何恢复和重试。
4. 无菜谱做饭中未匹配库存是否允许参与成品保存。若允许，它仍不能进入菜谱营养计算。
5. 同名菜谱是否沿用 FR-003 的“不覆盖”规则。当前产品倾向沿用。

#### 初步产品决定

1. 主要食材克重用于营养和菜谱生成。调味品默认不进入营养计算。
2. 成品保存后必须进入菜谱确认，不直接结束。
3. 菜谱确认后加入候选菜池。
4. 成品需要进入记餐成品选择器，不能只成为菜谱。
5. 首页入口放在“本周食谱”卡片内。

#### 后端评估

采用独立 RPC 和两步事务，不扩展现有 `save_cook_session`。现有 RPC 以菜谱条目作为营养克重来源，若只把 `p_recipe_id` 改为可空，会失去可信克重来源，并把有菜谱和无菜谱两种校验混在同一个接口中。

推荐并已实现的数据流：

```text
search_cook_inventory
→ 用户选择当前库存批次
→ 用户分别确认库存扣减数量和主要食材克重
→ save_cook_session_without_recipe
→ 创建真实 cook_session、cook_items、库存流水并扣库存
→ 成品立即进入记餐成品选择器
→ get_cook_recipe_confirmation
→ create_recipe_from_cook_session
→ 创建 recipes、recipe_items 和 recipe_candidates
→ cook_session 关联新菜谱并改为 confirmed
```

库存扣减数量和营养克重保持分离。`quantityUsed + unit` 只用于扣减所选库存批次。`grams` 只用于 `cook_items` 营养计算和后续生成 `recipe_items`。例如库存可以扣 `0.5 盒`，同时记录用户实际称重的 `180g`；后端不会把“盒”换算成克。

未匹配库存允许通过 `p_unmatched_items` 按相同量词扣减，并写入 `cook_unmatched_items`。它不生成 `cook_items`，也不会进入营养或新菜谱。为保证成品可以可靠进入记餐选择器，第一版至少需要一个已匹配食材和正数克重。调味品由前端默认不放入主要食材；后端只保存用户最终提交的主要食材。

保存成品和确认菜谱分为两个独立事务。第一步成功后，本锅已经真实存在且库存已经扣减，不因第二步失败而撤销。第二步发生同名、网络或权限错误时，本锅保持 `pending`。`get_kitchen_home` 会返回 `sourceType` 和 `recipeConfirmationStatus`，前端可以在重新打开应用后恢复确认入口。`get_cook_recipe_confirmation` 返回本锅已确认克重、未匹配库存和当前确认状态，用户无需重新填写做饭数据。

现有表足以保存业务数据，只给 `cook_sessions` 增加 `source_type`、`recipe_confirmation_status` 和 `recipe_confirmed_at`。`recipe_id` 在本锅待确认时为空，确认后指向从本锅生成的菜谱。`operation_requests` 增加 `save_cook_without_recipe` 和 `create_recipe_from_cook_session` 两种操作类型。

同名规则沿用 FR-003，不覆盖已有菜谱，返回 `DUPLICATE_RECIPE_NAME`。两步写入各自使用幂等键。同键同请求返回第一次成功结果；同键不同请求返回 `IDEMPOTENCY_CONFLICT`。网络结果未知时使用原键调用 `get_operation_result`。菜谱确认成功后使用新键再次确认返回 `CONFLICT`，不会生成第二份菜谱。

直接新增、修改或删除 `cook_sessions`、`cook_items` 和 `cook_unmatched_items` 的前端权限已经移除。两个写入 RPC 从 `auth.uid()` 取得用户，验证库存、食材、本锅和菜谱归属。跨用户引用统一返回 `INVALID_REFERENCE`。

#### 最终决定与原因

第一版采用“先保存成品，再确认菜谱”的两步事务。理由是食物已经做成后，菜谱命名或候选池写入失败不应撤销真实库存扣减，也不应让成品无法记餐。通过本锅状态和读取 RPC 恢复第二步，可以同时保证真实数据和可重试体验。

无菜谱做饭新增独立 RPC，不修改已有有菜谱做饭契约。主要食材必须匹配当前用户已有食材，并提交正数克重。未匹配库存可以扣减，但不能进入营养和新菜谱。同名菜谱不覆盖。

#### 后端实现与远端验证

远端迁移、RPC、RLS、幂等和类型已经完成。已验证：克重库存扣减、同量词库存扣减、未匹配库存扣减、本锅营养、成品选择器、厨房首页待确认恢复、从本锅生成菜谱与候选记录、别名无关的跨用户隔离、相同请求重试、同键冲突、同名拒绝、库存不足回滚、单位冲突回滚、缺少克重拒绝、直接表写入拒绝和网络结果查询。

测试数据使用两个临时隔离账号，结束后已清理。当前 43 项前端自动测试和生产构建通过；FR-004 新页面的加载、失败和恢复状态仍由前端接入时补充验证。

#### 验收标准

1. 用户可以从当前库存选择至少一个已匹配主要食材，并填写正数克重。
2. 保存成品在一个事务中扣减全部库存、写库存流水、创建 `cook_sessions`、`cook_items` 和可计算营养；任一步失败全部回滚。
3. 保存后的成品立即可被 `search_meal_components('cook_session', ...)` 读取。
4. 未匹配库存允许扣减并保留名称，但不进入 `cook_items`、营养和 `recipe_items`。
5. 菜谱确认从本锅的 `cook_items` 创建菜谱条目和候选记录，不信任前端重新提交的克重列表。
6. 菜谱确认失败时，本锅保持 `pending`，厨房首页和确认读取接口可以恢复。
7. 同名不覆盖。相同请求不重复扣库存、创建成品、菜谱或候选记录。
8. 跨用户不能读取确认草稿，也不能引用他人的库存、本锅或食材。
9. 库存不足、单位冲突、无正数克重、状态冲突和网络结果未知都有稳定处理方式。

## 9. 项目级思考日志

这里记录不属于某一个具体功能，但会影响整体方向的思考。每次只追加，不覆盖旧记录。

### 2026-07-12 · 确定三对话协作方式

决定由“梳理饮食追踪项目进度”作为产品主对话。当前对话负责后端实现，“开发 diet-tracker React 前端”负责前端实现。

选择这一方式的原因是，新需求主要从界面设计和使用流程中产生。产品主对话保存完整的需求背景，并将已经梳理清楚的问题分别交给前端和后端评估。前后端的技术限制和实现成本返回主对话，由主对话综合后决定是否实施。

### 2026-07-12 · 明确前端与后端的执行指令

前端和后端每次开始相关工作前，都需要先读取 `docs/feature-requests.md` 和 `docs/data-contract.md`。

后端只在需求状态为 `approved` 后实施涉及数据库、RLS、迁移、RPC 或数据导入的变化。评估阶段需要将可行性、数据结构影响、安全影响、工作量边界和待确认问题写回对应需求。实现并验证后，后端更新数据契约，将需求改为 `backend_ready`，并通知产品主对话。

前端只使用数据契约中标记为“已支持”的能力。界面出现新的数据需求时，前端记录其界面和交互影响，不自行新增字段、接口或模拟为真实能力。需求经产品主对话确认并且后端完成后，前端接入真实接口，完成加载、空、错误和保存失败状态的验证，将需求改为 `frontend_connected`，并通知产品主对话。
