# Diet Tracker · 需求与思考记录

最后更新：2026-07-12

## 1. 这份文档的作用

这份文档是三个 Codex 对话共享的需求记录，也是产品思考过程的长期存档。

它负责保存：

1. 新想法最初是怎么产生的。
2. 用户希望解决什么问题。
3. 界面、前端和后端分别受到什么影响。
4. 讨论中考虑过哪些方案。
5. 最终采用或放弃了什么，以及原因。
6. 需求后来发生过哪些变化。

已经确认并可以执行的接口定义写入 `docs/data-contract.md`。本文件不代替数据契约。

## 2. 三个对话的职责

| 对话 | 职责 |
|---|---|
| 梳理饮食追踪项目进度 | 产品主对话。记录想法、梳理使用流程、决定优先级、汇总前后端反馈并验收 |
| 当前后端对话 | 评估数据库、Supabase、安全、数据迁移和接口影响，并完成后端实现 |
| 开发 diet-tracker React 前端 | 评估页面、交互、客户端状态和接口接入，并完成前端实现 |

## 3. 状态定义

| 状态 | 含义 |
|---|---|
| `idea` | 正在记录和梳理，还没有要求前后端实现 |
| `needs_review` | 等待前端或后端评估 |
| `approved` | 产品方案已经确认，可以安排实现 |
| `backend_ready` | 后端已经完成并验证，前端可以接入 |
| `frontend_connected` | 前端已经接入，等待整体验收 |
| `done` | 已经验收完成 |
| `paused` | 暂时不做，但保留思考过程 |
| `rejected` | 决定不做，必须记录原因 |

## 4. 共同工作规则

1. 新需求不能只保存在某个对话中。主对话需要为它建立一个需求编号。
2. 三个对话开始相关工作前，都先读取本文件和 `docs/data-contract.md`。
3. 界面产生新数据需求时，先记录需求，再由前后端分别评估。
4. 前端不能根据界面自行增加数据库字段。后端也不能在产品流程未确认时替产品做决定。
5. 后端完成数据库迁移或接口后，需要同步更新 `docs/data-contract.md`。
6. 每次需求内容、状态、方案或负责人发生变化，都要在该需求的“更新记录”中追加一行。旧记录不得覆盖。
7. 对话之间的消息只负责提醒。完整信息以本文件和 `docs/data-contract.md` 为准。

## 7. 需求详情

### FR-001 · 小票识别并导入单品

**状态：** `needs_review`  
**提出位置：** 当前后端对话  
**当前负责人：** 前端/后端评估  
**最后更新：** 2026-07-12

#### 原始想法

单品选择器是否可以通过识别购物小票，把购买的商品直接接入饮食追踪工具。

#### 希望解决的问题

减少手动搜索和录入购买食品的操作。用户买完食物后，不想再次手动把蓝莓、鸡蛋、牛奶这类商品逐个搜索、添加到工具中。

#### 产品流程草案

第一版产品路径先按“库存导入”处理，不直接把小票商品变成可记餐单品。

```text
厨房首页
→ 冰箱库存
→ 更新库存
→ 选择拍照扫描小票或 PDF 导入小票
→ 上传后进入识别中状态
→ 系统生成待确认小票草稿
→ 用户逐项确认、修改、忽略或合并
→ 确认入库
→ 商品进入冰箱库存
→ 后续在做饭流程或库存列表中使用这批数据
```

用户确认页需要按识别状态分层：

1. 已匹配已有食材：显示标准名称、量词、数量，用户只确认数量和存放位置。
2. 可能匹配：显示原始小票名称和推荐匹配项，用户选择正确食材。
3. 未匹配：用户可以改名、选择已有食材、标为库存占位，或忽略。
4. 非食物或不追踪项目：用户可以忽略，不写入库存。

“开始使用这批数据”的第一入口是库存，不是记餐。

1. 在厨房首页的“冰箱库存”看到新增商品。
2. 在做饭流程中从库存选择食材，并确认本次用量。
3. 已匹配到 `ingredients` 且已有营养和标准份量的数据，未来才可以进入单品选择器。
4. 未匹配或无营养信息的商品只作为库存占位，不参与营养计算。

#### 当前尚未确认的问题

1. OCR/AI 识别是前端直接调用第三方，还是后端/Supabase Edge Function 处理。
2. 是否需要保存小票图片原图、识别文本和导入历史。
3. 当前 `inventory` 留位表是否足够，还是需要新增小票导入草稿表、草稿条目表和商品别名表。
4. 商品匹配已有 `ingredients` 的规则是什么：精确名称、别名、人工选择，还是 AI 建议。
5. 未匹配商品是否允许创建库存占位项。如果允许，它是否能在没有营养数据时进入做饭流程。
6. 第一版支持图片拍照、相册图片、PDF 三者中的哪些。
7. 入库确认后是否需要支持撤销或回滚本次导入。

#### 候选方案

**方案 A：库存优先，推荐。**
小票识别结果只进入库存确认流程。只有匹配到已有 `ingredients` 的商品才和营养系统产生连接。优点是符合当前厨房设想，风险低，不会把无营养数据商品误当作可记餐单品。缺点是不能立刻解决“单品选择器自动新增大量商品”。

**方案 B：食材库优先。**
小票商品确认后直接创建或补充 `ingredients`。优点是单品选择器增长快。缺点是小票通常没有营养信息，容易制造不可计算或错误计算的数据。

**方案 C：混合导入。**
确认页让用户选择“入库存”或“加入食材库”。优点是灵活。缺点是第一版交互和数据模型更复杂，容易把库存、食材库和营养库混在一起。

当前产品判断采用方案 A 作为评估基线。

#### 前端评估

待评估。请前端重点评估：

1. 厨房线需要新增或调整哪些页面：导入入口、识别中、确认列表、匹配选择、完成状态。
2. 确认页如何呈现已匹配、可能匹配、未匹配、忽略四类状态。
3. 拍照、相册图片、PDF 导入在浏览器/PWA 中的可行性和限制。
4. 用户修改数量、量词、名称、存放位置时，前端状态如何组织，是否需要草稿保存。
5. 确认入库失败时如何保留用户已经修正的结果。

#### 后端评估

**结论：** 当前 `inventory` 表可以保存确认后的库存行，但无法承担小票草稿和导入历史。采用“库存优先”需要新增导入主表与条目表；建议同时加入别名表，以便人工确认过的商品在下次导入时自动匹配。当前不应开始迁移或实现，等待产品主对话确认范围。

##### 1. 当前数据库的支持边界

`inventory` 已有 `ingredient_id`、数量、单位、存放位置、购买日期、价格和 `receipt_raw_name`。因此，一条确认过的小票商品可以写入一条库存记录：匹配成功时填写 `ingredient_id`，未匹配时保持 `ingredient_id` 为空，并保留用户确认后的商品名称作为库存占位。

但现有表没有以下能力：上传文件的归属和状态、OCR 原始文本、每条识别结果、匹配置信度、用户在确认页的修改、一次导入产生了哪些库存行、失败重试和重复确认保护。因此不能把小票草稿直接写入 `inventory`，否则用户还没确认的数据会污染真实库存。

##### 2. 建议的数据结构

建议新增以下三张表，并对 `inventory` 做最小扩展。

| 结构 | 作用 | 第一版建议字段 |
|---|---|---|
| `receipt_imports` | 一次上传和识别任务 | `id`、`user_id`、`storage_path`、`source_type`、`file_hash`、`status`、`merchant_name`、`purchased_on`、`raw_text`、`error_message`、`created_at`、`confirmed_at` |
| `receipt_items` | 小票中的一行草稿及用户确认结果 | `id`、`receipt_import_id`、`position`、`raw_line`、`raw_name`、`raw_quantity`、`raw_unit`、`raw_price`、`ingredient_id`、`match_status`、`match_confidence`、`confirmed_name`、`confirmed_quantity`、`confirmed_unit`、`storage`、`action`、`inventory_id` |
| `ingredient_aliases` | 用户确认过的商品名到既有食材的映射 | `id`、`user_id`、`ingredient_id`、`alias`、`normalized_alias`、`merchant_name`、`created_at` |

`receipt_imports.status` 建议限制为 `uploaded`、`processing`、`ready_for_review`、`confirmed`、`failed`、`cancelled`。`receipt_items.match_status` 建议限制为 `matched`、`possible_match`、`unmatched`、`ignored`。`action` 建议限制为 `add_to_inventory`、`ignore`。

`inventory` 建议增加 `receipt_item_id`，并为它建立唯一约束。这样一条小票条目最多只能生成一条库存记录，确认请求重试时也不会重复入库。是否需要额外的 `display_name` 字段需要产品确认：已匹配条目可显示 `ingredients.name`，未匹配库存占位则需要显示用户确认后的名称，现有 `receipt_raw_name` 的语义不足以同时表达“原始识别名称”和“确认后的展示名称”。

##### 3. OCR/AI 的放置方案

有三种路径：

1. 手动 mock：前端或数据库预先生成草稿。它适合验证确认页交互，不提供真实识别能力。
2. 浏览器直接调用外部 OCR/AI：实现最短，但密钥会暴露给客户端，且难以统一鉴权、限额和错误处理，不建议采用。
3. Supabase Edge Function 调用外部 OCR/AI：推荐。浏览器只上传私有文件并调用受登录保护的 `process_receipt`；函数验证文件归属后，使用服务器端密钥调用外部识别服务，再写入草稿表。

建议分两步推进：先用手动 mock 验证前端确认流程；获得 `approved` 后，再实现“私有 Storage + Edge Function + 外部 OCR/AI”。Edge Function 是调用和保护密钥的位置，OCR/视觉识别本身仍由外部服务完成。

##### 4. RLS、图片和用户隔离

小票包含购买信息，原图必须放在私有 Storage bucket，例如 `receipt-source`，对象路径固定为 `{user_id}/{receipt_import_id}/original`。不使用公开 bucket 或公开 URL。

Storage policy 只允许已登录用户读取、上传和删除自己用户 ID 文件夹中的对象，并限制允许的 MIME 类型与文件大小。第一版建议先限定 JPEG、PNG 和 WebP；是否支持 PDF 要在产品范围确认后再加入，因为外部识别服务对 PDF 的能力不同。

`receipt_imports` 使用与现有用户表相同的直接 `user_id = auth.uid()` RLS。`receipt_items` 的所有策略通过所属 `receipt_imports.user_id = auth.uid()` 验证。`ingredient_aliases` 同样按 `user_id` 隔离。

Edge Function 必须验证调用者 JWT，并验证传入 `receipt_import_id` 属于该用户。若函数使用 service role 写入草稿，必须从已验证的 JWT 获取用户 ID，不能信任客户端传来的 `user_id`。外部 OCR/AI 密钥只存放在 Edge Function 的服务器端环境变量中，不进入前端环境变量或仓库。

##### 5. 确认入库、重复保护和撤销

确认入库必须是一个 RPC，例如 `confirm_receipt_import(import_id, items)`，在单一数据库事务中完成：锁定导入记录、验证归属与状态、验证提交的条目属于该导入、插入或更新库存、写回每条 `inventory_id`、将导入改为 `confirmed`。任何一步失败时，全部回滚。

重复保护至少需要两层：`receipt_imports` 以 `(user_id, file_hash)` 提示同一文件已经上传；`inventory.receipt_item_id` 的唯一约束阻止同一条目重复入库。RPC 对已经 `confirmed` 的导入应返回既有结果，而不是再次写入。

第一版不建议承诺“任意时刻一键撤销”。草稿阶段可以直接取消。确认后应保留导入历史和条目到库存的链接。若后续库存会被做饭或手工修改，可靠撤销需要新增库存流水表，不能简单删除库存行。第一版可先把“撤销已确认导入”列为下一期能力，或仅允许在所有关联库存行未被后续修改时撤销。这一范围需要产品主对话确认。

##### 6. 获得批准后需要写入数据契约的内容

当前 `docs/data-contract.md` 只覆盖第一版记餐链路，厨房和库存仍是占位页，因此现在不应把上述接口标记为“已支持”。获得批准并完成迁移后，至少需要新增：

1. `ReceiptImportStatus`、`ReceiptItemMatchStatus`、`ReceiptImport`、`ReceiptItem` 和库存展示行的数据类型。
2. 创建导入、读取草稿、更新草稿条目、确认入库、取消草稿的 RPC 或 Edge Function 调用方式、入参和返回值。
3. 文件上传约束：支持的格式、大小上限、私有 bucket 规则和失败状态。
4. 匹配规则：别名匹配、推荐匹配、人工选择与未匹配库存占位的边界。
5. 幂等和错误语义：重复文件、识别失败、确认失败和已确认导入重试时的前端行为。

##### 建议的第一版后端范围

实现一张私有图片上传、一次识别草稿、人工确认、写入库存和防重复确认。暂不承诺 PDF、自动创建 `ingredients`、营养计算、复杂撤销、库存扣减或跨用户共享食材库。

## 9. 项目级思考日志

### 2026-07-12 · 确定三对话协作方式

决定由“梳理饮食追踪项目进度”作为产品主对话。当前对话负责后端实现，“开发 diet-tracker React 前端”负责前端实现。

选择这一方式的原因是，新需求主要从界面设计和使用流程中产生。产品主对话保存完整的需求背景，并将已经梳理清楚的问题分别交给前端和后端评估。前后端的技术限制和实现成本返回主对话，由主对话综合后决定是否实施。

### 2026-07-12 · 明确前端与后端的执行指令

前端和后端每次开始相关工作前，都需要先读取 `docs/feature-requests.md` 和 `docs/data-contract.md`。

后端只在需求状态为 `approved` 后实施涉及数据库、RLS、迁移、RPC 或数据导入的变化。评估阶段需要将可行性、数据结构影响、安全影响、工作量边界和待确认问题写回对应需求。实现并验证后，后端更新数据契约，将需求改为 `backend_ready`，并通知产品主对话。

前端只使用数据契约中标记为“已支持”的能力。界面出现新的数据需求时，前端记录其界面和交互影响，不自行新增字段、接口或模拟为真实能力。需求经产品主对话确认并且后端完成后，前端接入真实接口，完成加载、空、错误和保存失败状态的验证，将需求改为 `frontend_connected`，并通知产品主对话。
